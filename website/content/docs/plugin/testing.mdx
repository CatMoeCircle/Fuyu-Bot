插件出问题通常不是「代码写得不对」，而是「没被加载」「加载了但没订阅上」「订阅了但请求拼错」。
这三步各有对应的工具，全都不需要 Telegram 账号。

| 命令 | 干什么 | 需要账号吗 |
| --- | --- | --- |
| `fuyubot-sdk check <产物>` | **静态**读导出符号，不 dlopen | 否 |
| `fuyubot run --replay <文件>` | 把一批更新灌进管线后退出，不接 TDLib | 否 |
| `fuyubot plugin install <路径>` | 复制产物（＋脚本同伴）进插件目录 | 否 |
| `fuyubot plugin list` | 真的加载一次，看插件名与 ABI 版本 | 否 |
| `fuyubot run` | 真登录、真更新 | 是 |

## 静态检查：`fuyubot-sdk check`

```bash
fuyubot-sdk check target\debug\fuyubot_plugin_demo.dll
```

```text
文件：target\debug\fuyubot_plugin_demo.dll
格式：Pe / X86_64 / Dynamic
导出符号：
  [ok] plugin_init          必需
  [ok] plugin_start
  [ok] plugin_stop
  [ok] plugin_free_string
ABI 版本：宿主是 1。插件报的版本**只能运行时判定**——它在 `PluginHandle.abi_version`
     里，是 `plugin_init` 的返回值，不是静态符号（见 docs/abi-contract.md）。
结论：可以加载。
```

- **非零退出 = 宿主会拒绝加载**（缺必需的 `plugin_init`，或根本不是动态库），可以进 CI。
- 它**不加载、不运行**：走 `object` 解析 PE / ELF / Mach-O 的导出表，不碰 `dlopen`
  （`dlopen` 会在宿主进程里跑插件的初始化代码，那已经算「加载」了）。
- 因此它**看不到 ABI 版本**——版本是 `plugin_init` 的**返回值**，不是符号。它只会如实报
  「只能运行时判定」，不编一个看起来可信的结论。

## 回放：不接账号也能验插件

```bash
fuyubot run --replay examples\replay\new_message.json --plugin-dir <插件目录>
```

回放把文件里的更新（单个对象或对象数组）灌进六阶段管线后退出：**不接 TDLib、不用账号**，
插件发出的请求只留档不发。输出三样东西：

1. 每条更新的 `UpdateOutcome`：

```text
回放 updateNewMessage → UpdateOutcome { update_type: "updateNewMessage", listeners: 1, warnings: [] }
```

2. 插件打的日志（`HostRuntime::log_lines`，上限 256 行）；
3. 插件发出去的请求：`#请求号 方法名 参数`。

| 参数 | 说明 |
| --- | --- |
| `--replay <文件>` | 要回放的更新；对象或对象数组 |
| `--plugin-dir <目录>` | 覆盖插件目录（默认取 `fuyubot.toml` 的 `plugins.dir`） |
| `--replay-wait <MS>` | 回放后的静默窗口；不填时脚本插件 2000ms、纯原生插件 150ms（上限 60 秒） |

脚本插件在**另一个进程**里跑，反应要经管道回来，还可能捎带网络请求——窗口太短会把最终答复漏掉。

<Callout type="info">
  回放**故意不接 TDLib**（`AGENTS.md` 约束 38）：它要在任何机器上离线可跑，接了就要账号与网络。
  所以回放能证明「插件收到更新后做出了正确判断、发出了正确请求」，**不能**证明真 Telegram 认这些参数。
</Callout>

## 安装

```bash
fuyubot init --dir . --name demo                        # 生成 fuyubot.toml + plugins/
fuyubot plugin install plugins/demo --config fuyubot.toml
fuyubot plugin list
```

```text
已安装 F:\…\plugins\demo.dll
```

- 传**工程目录**时会把旁边的 `.py` / `.js` / `.ts` / `.pyi` 一起拷；传单个 dll 时看不到脚本在哪，
  **脚本插件请传工程目录**。
- `plugin install <工程目录>` 只看 `<工程>/target/{release,debug}` 与工程目录本身。若插件是**当前
  workspace 的成员**（本仓的 `examples/*`），`cargo build -p <crate>` 的产物默认落在仓库根 `target/`，
  于是它找不到——加 `--target-dir <工程目录>/target`，或直接指着产物装。

## 装完还是不响？

| 症状 | 先看 |
| --- | --- |
| `check` 报 `[缺] plugin_init` | crate 是不是 `crate-type = ["cdylib"]`；C++ 的四个符号在不在 `extern "C"` 里 |
| 日志里有「跳过 xxx」 | ABI 版本不匹配，或 `dlopen` 失败（缺兄弟 DLL：把依赖放在插件旁边，加载器会先查库自己的目录） |
| 加载了但一条事件都没收到 | 订阅句柄是不是被 drop 了（Rust 侧 `let _ =` 会立刻退订） |
| 脚本插件 `plugin_start` 报错 | 脚本与 cdylib 是否**同名同目录**；`host.run()` 是不是最后一行；解释器在不在 PATH |
| 请求发出去了但没收到响应 | 回放里本来就不会有响应（请求只留档）；真环境下等的是 `"response"` 通道，见 [调用 TDLib](./tdlib.mdx) |

要查 TDLib 的方法名与参数名，用 `fuyubot-sdk td-methods --filter <片段>` / `td-method <名字>`；
契约与所有权规则见 [ABI 契约](./abi.mdx)。
